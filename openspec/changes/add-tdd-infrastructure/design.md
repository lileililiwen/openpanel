# Design: Add TDD Infrastructure

## Context

The current test layer is ad-hoc: each crate has a `tests` module
with ad-hoc unit tests. There is no shared fixture crate, no per-test
DB isolation, no integration tests that exercise the real axum
router, no property-based coverage, no E2E CLI coverage. The risk is
that future changes will pass tests while hiding real bugs — exactly
the failure mode the project standard prohibits.

This change establishes the conventions, fixtures, and tooling so every
future change is forced to write tests first (in the format defined
by this spec), exercise real production code through `TestServer`,
and cover domain invariants with property-based tests.

## Goals / Non-Goals

**Goals:**

- One workspace crate (`openpanel-test-support`) that owns every test
  helper, mock, and fixture.
- A hard rule that tests live in one of four categories with a fixed
  location per category.
- Per-test DB isolation via `TestDb` (RAII wrapper over a SQLite
  file under `/tmp/openpanel-test/<uuid>.db`).
- `mockall`-based mocks for every port in `openpanel-domain` and
  `openpanel-core::AuditService`.
- `proptest` for domain invariants.
- `TestServer` that boots the real axum router for HTTP integration.
- An E2E test layer that spawns the `openpanel` binary as a child
  process.
- A new "Testing" task group at the top of every future spec's
  `tasks.md`.
- Repeatable: `cargo test --workspace` is order-independent and
  environment-independent.

**Non-Goals:**

- Mutation testing (`cargo-mutants`) — not in offline cache; deferred.
- Coverage thresholds / CI enforcement — covered by the follow-up
  `add-quality-engineering-infrastructure` change.
- Property-based tests for every primitive — only domain invariants
  in this change.
- `testcontainers`-driven MySQL/Postgres integration tests — wired
  but gated on a daemon being available; deferred to a later change
  for the actual container fixtures.
- Performance / load tests.

## Decisions

### 1. One workspace crate for test helpers

**Decision**: All test helpers live in `crates/openpanel-test-support/`.
Other crates declare `dev-dependencies = { openpanel-test-support = ... }`.

**Rationale**: Centralising fixtures prevents drift between crates.
A `TestDb` built differently in two crates would leak state across
tests.

**Alternatives considered**:

- A `tests/common/mod.rs` file shared via `path = "tests/common"` —
  doesn't work because tests are compiled per-crate.
- Per-crate helpers with a `pub mod test_util` — would duplicate
  fixtures.

### 2. `TestDb` uses SQLite file under `/tmp/openpanel-test/`

**Decision**: `TestDb::new()` creates a fresh SQLite file under
`/tmp/openpanel-test/<uuid>.db`, calls `SqliteDriver::connect`,
applies all migrations, and returns the pool. `Drop` removes the
file.

**Rationale**: SQLite files are cheaper than in-memory DBs when
multiple connections need to share state (e.g. a background server
task and the test thread). The file-based approach makes the test
DB inspectable from the shell during debugging.

**Alternatives considered**:

- `sqlx::sqlite::SqlitePoolOptions::connect_with(":memory:")` — fast
  but doesn't survive across processes (no issue for in-process
  tests, but rules out some integration scenarios).
- One fixed `/tmp/test.db` — fails repeatability (parallel tests).

### 3. Mocks via `mockall`

**Decision**: Every port trait gets a `Mock*Repository` struct
generated by `mockall::mock!`. Tests call `.expect_<method>()
.times(n).returning(Ok(...))` to set expectations.

**Rationale**: `mockall` is the standard Rust mocking framework; it
generates type-safe mocks at compile time so a test using a renamed
trait method fails to compile rather than failing at runtime.

**Alternatives considered**:

- Hand-rolled `Arc<Mutex<...>>`-based fakes — verbose, error-prone,
  currently present in some crates.
- `mockall::automock` — same machinery, less ceremony.

### 4. `TestServer` boots real axum

**Decision**: `TestServer::new(db: TestDb, modules: ...) -> Self`
binds a `TcpListener` on `127.0.0.1:0` (kernel-assigned port),
constructs an `axum::Router` via `openpanel_api::build_router`,
spawns the server on the current tokio runtime, and returns the
address. Tests interact via `reqwest::Client::new()`.

**Rationale**: This exercises the actual production code path
(routing, middleware, error mapping) — not a hand-rolled mock that
might drift from reality.

### 5. E2E CLI tests spawn the real binary

**Decision**: `tests/cli/<command>.rs` invokes
`std::process::Command::new(env!("CARGO_BIN_EXE_openpanel"))` with
`OPENPANEL__DATABASE__URL` pointing at a per-test `TestDb`.

**Rationale**: The CLI binary is the same artifact a user installs;
testing it ensures `openpanel migrate`, `openpanel user create`, etc.
actually work as documented.

### 6. Property-based tests only for domain invariants

**Decision**: `proptest` is used to assert domain invariants
(`Site::new` rejects all bad inputs, `Password::hash`/`verify`
roundtrip). It is NOT used for I/O paths (those get integration
tests).

**Rationale**: proptest is good at finding edge cases in pure
transformations. I/O paths are stateful and better tested with
integration tests.

### 7. Skip, don't fail, when external deps are missing

**Decision**: Tests that need `mysql`, `nginx`, etc. detect
absence via `which mysql` and `tokio::task::spawn(async { ...ok_or
(false) })`, then `return` early with `eprintln!("skipped: ...")`
and the test is marked `#[ignore]`-equivalent.

**Rationale**: The project must build and test in dev environments
without those binaries installed.

### 8. Mandatory "Testing" task group

**Decision**: Every `tasks.md` MUST start with `## 1. Testing`. The
tasks in that group MUST be implemented (and failing — TDD red phase)
BEFORE any implementation task group.

**Rationale**: This is the core TDD discipline. Putting tests first
in the file makes skipping them harder than doing them.

## Risks / Trade-offs

- **Risk**: `proptest` slows down `cargo test` → *Mitigation*: each
  proptest test runs 100 cases by default; CI can raise to 1000.
- **Risk**: `mockall` derive macros add compile time → *Mitigation*:
  they only fire in `#[cfg(test)]` builds; release build unaffected.
- **Risk**: `/tmp/openpanel-test/<uuid>.db` files leak if a process
  is killed → *Mitigation*: a `scripts/clean-tests.sh` helper
  (informational) deletes anything older than 1 day; CI runner uses
  ephemeral `/tmp`.
- **Risk**: Test runtime for integration tests is non-trivial
  (~50ms per test due to axum boot) → *Mitigation*: parallel test
  execution; cargo-nextest recommended.

## Migration Plan

- No existing data to migrate.
- The change adds the test-support crate and rewrites one test per
  bounded context as a "before" demonstration. Existing unit tests
  continue to work; new tests follow the new conventions.
- Future changes adopt the conventions; legacy ad-hoc tests are
  gradually migrated.

## Open Questions

- Should we ship a `tests/integration/main.rs` smoke test that
  exercises every route? → *Default: yes*, as `tests/integration/smoke.rs`.
- Should the audit `MockAudit` use `mockall::Sequence` to assert
  ordering? → *Default: no*; ordering is the framework's contract,
  not the test's responsibility. Tests assert presence and metadata.
- Should `TestDb` also include the audit schema? → *Default: yes*;
  the `audit.sql` migration runs alongside the per-module migrations.
